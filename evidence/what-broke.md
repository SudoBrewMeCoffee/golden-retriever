# What broke

Every real failure hit while building this, with root cause, fix, and the control that stops it recurring.

| # | What happened | Root cause | Fix | Control added so it can't recur |
|---|---|---|---|---|
| 1 | Pre-flight review: the SSH access guardrail (`rhel9cis_sshd: {allow_users: rocky}`) would have been silently ignored by the CIS role | The ansible-lockdown role reads flat variables (`rhel9cis_sshd_allowusers`, `rhel9cis_sshd_allowgroups`); a nested dict with different key names is just an unused variable. Ansible doesn't warn on unused vars | Renamed to the role's real variables; pinned the role to release 2.4.2 instead of `main` | Every guardrail var is grep-checked against the pinned tag's `defaults/main/main.yml` before a role bump; role pinned to a tag, never a branch |
| 2 | Pre-flight review: CIS 5.2.4 would strip NOPASSWD sudo from the `rocky` build account mid-build | The role only exempts `ec2-user` and `vagrant` (AWS/Vagrant assumptions). On a Rocky GenericCloud image the cloud-init user is `rocky`, which has no password, so after 5.2.4 Packer's cleanup step (`sudo cloud-init clean`) and every admin sudo would fail - an image you can't administer | Added `rocky` to `rhel9cis_sudoers_exclude_nopasswd_list`; recorded as deviation D2 with justification (key-only automation account, no password) | Deviations register (`deviations.md`); Molecule verify asserts sudo still works for the admin account |
| 3 | Pre-flight review: pack defaults didn't match the estate (node `pve0`, storage `local-lvm`) | Defaults written from notes, not from the live estate. The node is `pve`; there is no LVM-thin store - VM disks are on ZFS (`local-zfs`) | Corrected in packer/ and terraform/ variables and the README | Pre-flight step: `pvesh get /nodes` + `pvesm status` before first apply |
| 4 | First boot of the "before" VM (300) took **10.69.1.222** from DHCP - the static address of CT260, a live production container on the estate. Duplicate IP on the LAN | The UniFi Core LAN DHCP pool is 10.69.1.100-254, and most KRONOS containers have static IPs *inside* that pool with no DHCP reservation, so the router believes those addresses are free | Spotted within a minute from the agent-reported IP; stopped VM 300, flushed ARP, sent gratuitous ARP from CT260, confirmed CT260 gateway + internet + services healthy. Re-addressed ch-mirror to fixed IPs 10.69.1.70-79 (outside the pool): 300=.70, Packer build=.71, 301=.72 | Packer and Terraform now set static IPs, never DHCP. Estate-wide fix raised for Graham: shrink the pool to 10.69.1.200-254 or add reservations for every static guest |
| 5 | `molecule test` crashed on import (`dataclasses has no attribute _is_type`) | pipx built Molecule's venv on Homebrew's newest Python (3.15); ansible-core 2.21 only supports up to 3.14 | Rebuilt the venv on Python 3.13 and pinned `ansible-core<2.22` | Toolchain versions recorded in README; CI runner uses the same venv |
| 6 | Molecule failed at dependency, then at create | (a) `community.docker` collection not declared; (b) Docker Desktop's credential helper isn't on PATH in a non-login shell | Declared all collections the role needs in `requirements.yml`; runner PATH includes Docker Desktop's bin dir | Collections are now part of the pinned requirements, installed the same way locally and in CI |
| 7 | `terraform fmt -check` / `packer fmt -check` failed on the first run of the gates | Hand-written HCL alignment | `terraform fmt` / `packer fmt` | Exactly what the pre-commit gate is for - it can't merge unformatted |
| 8 | Molecule container wouldn't start: `exec: "/usr/sbin/init": no such file or directory` | The official `rockylinux:9` container image is minimal - no systemd - but CIS controls are about services, so the test needs a real init | Small `Dockerfile.j2` on top of the official Rocky base adding systemd/sshd/sudo; no third-party test images | Test image is defined in the repo, so CI builds the identical environment |
| 9 | Converge stopped at the role's own pre-flight checks: (a) "You still have the default name for your authselect profile"; (b) reading the pre-flight code showed a second guard that would have failed the *Packer* build: with rule 5.2.4 on, the role refuses to run as a build user with no password - which is exactly `rocky` | The role is built to stop rather than lock you out, but it assumes an EC2/Vagrant-style user. Molecule connects as root so it never hit guard (b) - only reading the role's code revealed it | Set a site authselect profile name (`ch_mirror_cis`); disabled rule 5.2.4 outright as deviation D2 instead of only exempting the user | Read the pinned role's `tasks/main.yml` pre-flight asserts at every role bump; Molecule can't stand in for the real build user |
| 10 | Molecule idempotence failed on one task: `Create ansible facts file and levels applied` | The role writes a compliance facts file stamped with the run time, so it changes on every run by design - not a control | Molecule skips the `benchmark` tag only; the real image build still writes the facts file (useful audit metadata: benchmark version + levels applied) | Idempotence still covers every CIS control task |
| 11 | First Packer build hung at "Waiting for SSH" - the VM never came on the network | The Packer Proxmox plugin applies its own hardware defaults to the clone: **cpu kvm64**, ostype other. RHEL 9 / Rocky 9 require the x86-64-v2 instruction set; kvm64 doesn't provide it, so the kernel won't boot. Template 9200 had `cpu: host`, but the plugin overrode it | Cancelled the build; removed the orphaned build VM 9201 (Packer's own cleanup lost the API mid-interrupt); pinned `cpu_type = host` and `os = l26` in the Packer source | Build hardware is declared in code, not inherited; after any failed build, check for and remove the orphaned build VM |
| 12 | Molecule `verify` failed: `PermitRootLogin no` not in effect after hardening | Not a hardening bug - RHEL9-CIS detects it is in a container and switches off **78 controls** (SSH, firewall, SELinux, mounts, AIDE, crypto policy...) via `vars/is_container.yml`. A green Molecule run would have proved nothing about SSH. Caught only because verify asserted the *outcome* (`sshd -T`), not that a task ran | Split testing: Molecule proves role logic and the checks a container can prove; `ansible/verify-vm.yml` runs inside the Packer build against the real VM and fails the build if SSH, SELinux, auditd, firewalld or admin access aren't right; Wazuh SCA is the independent proof | An image can't be published unless the controls are verified on a real VM |
| 13 | Two Packer builds died mid-run with `no route to host` to the Proxmox API and the build VM, while the same commands run by hand worked | macOS **Local Network privacy**: a background job detached from its SSH session (`nohup ... &`) loses LAN access when the session closes, and the error it gets is EHOSTUNREACH. Proven with a 1-second ping monitor (failing) next to an interactive ping (fine), and a packet capture on Proxmox showing replies leaving correctly - the drop was on the Mac | Long jobs run in a held-open session instead of detached; orphaned build VMs removed each time | CI runner must run as a launchd service with Local Network permission, not a detached shell job |
| 14 | Third build hardened and verified the VM (414 tasks OK, verify gate 11/11) then failed at the very last step: `Error converting VM to template ... can't lock file lock-9201.conf - got timeout` - and Packer deleted the VM | The hardened guest took 91 s to shut down cleanly (Proxmox task log). The Packer plugin's default task timeout is 60 s, so it gave up and re-sent shutdown; the retries queued behind the still-running shutdown holding the VM lock | `task_timeout = 10m` in the Packer source | Read the Proxmox task log (`/var/log/pve/tasks`) before re-running - the cause was in the timestamps, not the Packer output |
| 15 | Caught in plan review, before apply: the Terraform plan for 301 showed `cpu.type = "qemu64"` | Same class as #11 - the bpg/proxmox provider has its own CPU default (qemu64) and doesn't inherit the template's `cpu: host`. Applied as-is, 301 would never have booted | Pinned `cpu.type = host` and `operating_system.type = l26` in Terraform | This is why the pipeline posts the plan and waits for a human: the plan is the review artefact, read it before approving |
| 16 | Pre-flight review of the Amazon Linux 2023 role (ansible-lockdown AMAZON2023-CIS 1.5.0): setting `amzn2023cis_level_2: false` would NOT have limited the build to Level 1 | In this role the level variables are read by no task - they only feed the audit/facts file. Level is selected by tags (`level1-server`), per the role README. Same class as #1: a guardrail var that looks right and does nothing | The AL2023 Packer build runs the role with `--tags level1-server`; vars kept only for the facts file and commented as such | Same rule as #1, applied to every new role: grep each guardrail var for a *task* that reads it, not just a default that declares it |
| 17 | Pre-flight review: the AL2023 role's own pre-flight (`tasks/main.yml`) asserts "root password is set" (CIS AL2023 4.6.6) and stops the play if not | The AWS KVM image ships root locked with no password. Setting one would bake a shared root secret into every VM from the template | Rule disabled (`amzn2023cis_rule_4_6_6: false`) and recorded as deviation AL-D2: root stays locked, root SSH off, SSH limited to `ec2-user` keys | Read the pinned role's pre-flight asserts at every role bump (as #9); deviations register per image (`deviations-al2023.md`) |
| 18 | First AL2023 build: hardening finished (312 ok, 0 failed) but the verify gate failed - `firewalld.service` didn't exist on the VM | In CIS Amazon Linux 2023 v1.0.0 the whole host firewall section (3.4) is **Level 2** - AWS assumes security groups do that job. A Level 1 run correctly installs no firewall, which on Proxmox (no security groups) means none at all. The RHEL 9 benchmark has the firewall in Level 1, so the same verify check had always passed there | Run the role's own firewall controls 3.4.1.2 + 3.4.2.1 by tag alongside Level 1 (firewalld on, default zone `public`, ssh allowed); recorded in AL-D1 as stricter-than-L1. Packer's cleanup removed the build VM | The verify gate asserts *outcomes* (service running), not levels or task counts - it's the same gate for both images, so a benchmark difference between distros can't ship silently (as #12) |
| 19 | Second AL2023 build: hardening (316 ok, 0 failed) and verify gate (11/11) passed, then the final cleanup step died: `/tmp/script_9998.sh: Permission denied` (exit 126) and Packer deleted the VM | Packer's shell provisioner uploads each inline script to `/tmp` and executes it there. CIS 1.1.2.4 (Level 1) sets `noexec` on `/tmp`; AL2023 mounts `/tmp` as tmpfs, so the role remounted it live mid-build. The Rocky GenericCloud image has no separate `/tmp` mount, so the RHEL build never hit this | `remote_folder = /home/ec2-user` on the post-hardening shell provisioner | Any provisioner that runs *after* hardening must not assume /tmp is executable - the hardened image is a different OS from the one the build started on |
| 20 | Caught before go-live, while registering the self-hosted runner: GitHub warns that self-hosted runners on public repos are unsafe. Review of `ci.yml` found two real exposures. (a) It ran on every `pull_request`, so a pull request from any fork would execute its own code on the runner host, which sits on the lab LAN next to the Proxmox token. (b) The saved `tfplan` was uploaded as a workflow artifact; a plan file holds input variable values (the API token), and artifacts on a public repo can be downloaded by others | The workflow was written for a private repo; the repo went public later and the CI design was not re-reviewed for that change | Self-hosted jobs run only for pushes, manual runs and PRs from branches in this repo (fork PRs get the GitHub-hosted checks only); the plan never leaves the runner host (kept outside the workspace and applied by run ID); credentials are read on the runner host by `tf.sh`, nothing secret is stored in GitHub; `kronos-prod` requires the owner's approval with admin bypass off | Any change of repo visibility, or a new self-hosted job, means re-reviewing triggers, artifacts and secrets first; the security model is written at the top of `ci.yml` |
| 21 | VM 301, deployed from image 1.0.1, raised an AIDE integrity alert on its first boot: `aidecheck.service` exited 7 with 131 differences (68 added, 1 removed, 62 changed). The build's verify gate had passed 28/28, and the post-deploy verify only showed "unit not OK" (issue #17) | Two causes, both from shipping an AIDE database inside the image: (a) **the baseline was taken part-way through the build** - the CIS role runs `aide --init` early, then later tasks change files (journal-remote packages and units, sysctl.d and audit rules, crypto-policy back-ends, passwd/group/shadow, the new kernel's boot entries, the release stamp and the aidecheck units themselves). This is most of the 131. (b) **per-instance first-boot changes** by cloud-init and the clone: hostname, hosts, machine-id, ifcfg-eth0, persistent-net rules. Either one alone alerts on every new VM, which teaches people to ignore AIDE. The 1.0.1 verifier missed it because it read unit state and never ran `aide --check` | Image 1.0.2: the Packer cleanup step, after every other change, deletes `aide.db.gz` and `aide.db.new.gz`. A new oneshot `aide-firstboot.service` (only when no database exists, after `cloud-final.service`) runs `aide --init` and moves the database into place, so each instance gets its own baseline after cloud-init. `aidecheck.service` now waits for it (`After=aide-firstboot.service`, `ConditionPathExists=` the database); the timer stays enabled, so CIS 1.3.2 still passes. Pre-flight catch: on Rocky 9, `cloud-final.service` and `cloud-init.target` are both `After=multi-user.target`, so hanging these units off `multi-user.target` would have been an ordering cycle; both are `WantedBy=cloud-init.target` instead | Two verify points: the build gate (`verify-vm.yml`) asserts the units are enabled; the new post-deploy check (`verify-deployed.yml`) proves the instance - first-boot baseline succeeded, database exists, **it runs `aide --check` and requires rc 0**, aidecheck not failed, one kernel matching `uname -r`, release stamp. A gate that only reads unit state can't catch a wrong baseline |
| 22 | First 1.0.2 test VM (303): the per-instance baseline worked - 131 differences down to 1 - but the boot-time `aidecheck.service` still exited 4, and `verify-deployed.yml` failed on `aide --check` rc 4. The one changed entry was `/boot/initramfs-<kernel>kdump.img` | `kdump.service` rebuilds the kdump initramfs on a new instance's first boot (19:41:38-19:41:53) and is not in `multi-user.target`'s ordering, so `After=cloud-final.service` did not wait for it. `aide --init` started at 19:41:41 and hashed the file mid-rebuild | `aide-firstboot.service` is also ordered `After=kdump.service` (ordering only - it does not pull kdump in). Template 9203 and VM 303 destroyed and rebuilt from the fixed code | Caught by the new post-deploy check doing what the 1.0.1 verifier couldn't: it runs `aide --check` on a fresh clone and requires rc 0 (`06-verify-deployed-1.0.2-attempt1.log`). Rule: a baseline is only valid once every first-boot writer has finished - check what is still `activating` when it runs, not just cloud-init |
